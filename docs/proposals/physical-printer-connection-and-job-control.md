# 提案：连接与驱动物理打印机

## 动机 / 用户故事

用户确认打印后，切好的 G-code 需要真正发送到指定打印机并开始打印。用户还需要知道打印进度和异常原因，并在完成后取得取件码。车间有多台不同品牌的打印机（Bambu、Prusa、Creality 等），因此需要用统一方式查看在线状态和耗材状态。

## 目标用户

- 发起打印、查看进度并取件的普通用户
- 查看设备与耗材状态的车间管理员

## 现有做法及不足

当前系统只能接收已经完成的 G-code，尚未形成从设备连接、任务下发、打印反馈到取件的闭环。不同品牌设备的协议和状态表达也不一致，用户无法用统一方式判断任务是否真正开始或失败。

## 本期范围

本期做：

- 接入打印机并统一上报在线、打印中、空闲、离线、缺料和错误状态。
- 把已确认任务的 G-code 下发到目标设备，支持开始、暂停和取消。
- 为下发、开始、暂停和取消分配稳定 `commandId`，支持幂等重试、设备回读和“结果未知”状态。
- 实时上报打印进度和事件时间线，覆盖首层、进度、完成或失败等阶段。
- 对料尽、附着失败等异常上报可理解的失败原因。
- 上报耗材余量，并在余量不足时告警。
- 打印完成后生成取件码，支持走完取件闭环。
- 设备离线时将下发动作降级为导出 G-code 文件。

本期明确不做：

- 不决定任务是否可以切片或是否应由用户确认；上游负责业务判断，设备执行层防御性校验不可伪造的 `executionGrant` 后才执行。
- 不做 Mesh 或切片处理，只接收成品 G-code。
- 不做设备固件管理或多车间调度算法。

## 关键决策与依据

### 备选方案

1. 让每种打印机协议直接暴露给上层业务。
   - 优点：接入初期可能较快。
   - 缺点：上层需要理解多种协议，新增品牌会扩大业务层复杂度。
2. 在设备适配层之上统一状态与任务语义，并对离线设备提供文件导出兜底。
   - 优点：上层流程稳定，新增品牌不会改变任务语义；离线时不会制造虚假的已发送状态。
   - 缺点：需要维护品牌协议到统一语义的映射。

### 本期选择

选择方案 2。

原因：本期的核心是执行已确认任务并形成可观察的打印闭环，而不是让打印机侧绕过上游确认。统一状态和任务生命周期可以隔离品牌差异；离线降级则避免把“导出文件”误报为“已发送”。

## 基本概念与信息结构

### 设备状态

- `online`: 设备是否可连接
- `status`: 在线、打印中、空闲、离线、缺料或错误
- `filament`: 当前耗材状态和余量

### 打印任务

- `gcode`: 已确认的成品 G-code
- `device`: 目标打印机
- `status`: 待下发、打印中、已暂停、已取消、已完成或失败
- `events`: 首层、进度、完成或失败等时间线事件
- `failureReason`: 失败原因
- `pickupCode`: 完成后生成的取件码
- `executionGrant`: 上游确认后签发、绑定任务/G-code/设备且不可复用到其他任务的执行许可
- `commands`: 每条命令的 `commandId`、类型、设备确认、状态和时间；状态至少包含 pending、acknowledged、unknown、succeeded、failed

## 原型 / 演示

设备列表展示打印机名称、品牌、统一状态和耗材余量。任务详情展示当前进度、事件时间线、异常原因以及开始、暂停、取消操作。设备不可用时，页面明确提供“导出 G-code”而不是显示已发送。

## 验收标准

### 例子 1：设备接入与状态变化

- 现状：不同品牌设备没有统一状态视图。
- 提议后的行为：接入一台打印机后，系统显示其统一状态，并能随设备状态变化更新。
- 验收：分别模拟在线、空闲、打印中、缺料、错误和离线状态，设备列表中的状态与耗材信息同步变化。

### 例子 2：下发已确认任务并跟踪进度

- 现状：已确认的 G-code 不能形成可观察的设备任务。
- 提议后的行为：将 `gcode` 和目标 `device` 提交为打印任务，设备开始打印后持续追加进度和事件。
- 验收：任务进入打印中后，进度递增，时间线至少出现首层、进度和完成或失败事件；任务状态与设备状态一致。

### 例子 3：异常与耗材不足

- 现状：用户无法知道打印为什么失败，也不能提前发现耗材不足。
- 提议后的行为：设备上报料尽、附着失败等事件时，任务失败并记录原因；余量不足时产生告警。
- 验收：模拟料尽和附着失败，任务均进入失败状态并返回对应原因；将耗材余量降到告警阈值以下时，设备状态产生余量不足告警。

### 例子 4：完成后的取件闭环

- 现状：打印完成后没有可用于取件的凭证。
- 提议后的行为：任务完成后生成取件码，并可在任务详情中查看。
- 验收：设备上报完成后，任务状态变为已完成且生成唯一取件码；取件流程能够使用该取件码完成交付记录。

### 例子 5：设备离线降级

- 现状：目标设备离线时不能可靠完成下发。
- 提议后的行为：系统不创建“已发送”假任务，而是提供 G-code 导出。
- 验收：对离线设备提交任务时，用户得到可下载的 G-code 文件和明确的离线反馈；系统不记录设备已接收或已开始打印。

### 例子 6：非法情况

- 现状：任务未确认、G-code 不完整或目标设备不可用时，存在绕过上游门控的风险。
- 提议后的行为：上游未确认时不签发 `executionGrant`；设备执行层不重新判断业务条件，但拒绝缺少或不匹配 grant、缺少成品 G-code 的请求，也不把不完整输入标记为已发送。
- 验收：未确认任务无法获得 `executionGrant`，伪造、过期或绑定其他任务的 grant 均被设备执行层拒绝；缺少成品 G-code 时拒绝下发；设备离线时只允许导出兜底，不产生打印任务成功记录。

### 例子 7：响应丢失后的命令重试

- 现状：设备已接收开始命令但 API 响应丢失时，客户端重试可能让同一 G-code 重复开打。
- 提议后的行为：相同 `commandId` 的重试返回原命令结果；无法确认结果时先进入 `unknown` 并从设备回读，不创建新开始命令。
- 验收：模拟设备已确认开始但响应超时，再以相同 `commandId` 重试；设备侧只出现一次开始动作，服务端通过回读把命令收敛为 acknowledged/succeeded。使用新 `commandId` 对已打印中的同一任务再次开始时被状态机拒绝。
