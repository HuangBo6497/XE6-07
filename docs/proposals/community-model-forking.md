# 提案：Fork 公开模型到“我的模型”

## 动机 / 用户故事

登录用户需要将允许衍生的公开模型 Fork 到“我的模型”，形成自己拥有的私有副本，同时保留原作者、源模型、源版本和授权关系，以便继续创作或修改。

## 目标用户

- 希望在公开模型基础上继续创作的登录用户
- 需要保留署名和授权关系的原作者
- 维护公共模型公开状态和授权约束的平台

## 现有做法及不足

公开模型与用户自己的模型之间没有受授权约束的复制入口。用户若手动下载再上传，容易丢失源版本、原作者和授权快照，也可能误把修改写回原模型或绕过后续发布审核。

## 本期范围

本期做：

- 在公开模型详情中提供 Fork 入口，并在确认前展示来源、作者、源版本和授权要求。
- 仅允许已登录用户 Fork 当前仍公开、未下架、文件可用且授权允许衍生的模型。
- Fork 成功后创建当前用户拥有的新私有模型，初始内容固定来自源模型当前经过审核的公开版本。
- 在“我的模型”中标记来源为“社区 Fork”，记录源模型、源版本、原作者和 Fork 时的授权快照。
- 原模型的统计、版本和文件不发生变化；Fork 后的修改只产生 Fork 模型自己的新版本。
- Fork 模型不会自动公开；后续公开时仍需经过发布审核，并保留必要署名和授权约束。
- 处理重复点击、网络重试、源模型下架和源模型产生新版本等状态变化。

本期明确不做：

- 不做上游同步、自动更新、模型差异比较、合并和冲突处理。
- 不做 Fork 网络图、排行榜、多人协作编辑或完整 Remix 编辑器。
- 不允许 Fork 后自动公开。
- 不绕过原授权或署名要求。

## 关键决策与依据

### 备选方案

1. 复制文件后作为普通私有模型，不保留来源关系。
   - 优点：数据结构简单。
   - 缺点：无法追溯原作者、源版本和授权，也难以保证后续署名。
2. 创建带来源快照的私有 Fork，并让 Fork 拥有独立版本生命周期。
   - 优点：保留授权与来源关系，原模型和 Fork 相互隔离，适合后续创作。
   - 缺点：需要处理幂等、防重复和源模型状态变化。
3. 与源模型保持自动同步。
   - 优点：可以获得源模型更新。
   - 缺点：会引入覆盖用户修改、差异合并和冲突处理，本期范围过大。

### 本期选择

选择方案 2。

原因：本期需要让用户安全地开始二次创作，同时保留源版本和授权事实；独立副本比自动同步更可控，也不会把用户修改写回原作者模型。

## 基本概念与信息结构

### Fork 模型

- `owner`: 当前 Fork 用户
- `sourceModel`: 源公开模型
- `sourceRevision`: Fork 时使用的源版本
- `sourceAuthor`: 原作者
- `licenseSnapshot`: Fork 时不可变的机器可读授权快照，包含许可名称与展示文案、`derivativesAllowed`、`attributionRequired`、`commercialAllowed` 和 `shareAlike`
- `status`: 私有、审核中、已公开等模型状态
- `origin`: 社区 Fork

### Fork 请求

一次确认请求只能创建一个副本。网络重试应返回同一个创建结果；用户明确重新操作后，才允许再次 Fork 同一源模型。

## 原型 / 演示

公开模型详情页在 Fork 前展示源模型、源版本、作者和授权要求。确认后跳转“我的模型”，新卡片标记“社区 Fork”并保持私有。授权禁止衍生或源模型状态不满足条件时，Fork 按钮不可用并说明原因。

## 验收标准

### 例子 1：允许衍生的公开模型

- 现状：用户无法在保留来源和授权的情况下开始二次创作。
- 提议后的行为：登录用户确认 Fork 后获得一个属于自己的私有副本。
- 验收：对一份已公开、未下架、文件可用且允许衍生的模型执行 Fork；“我的模型”出现社区 Fork 私有模型，记录源模型、源版本、原作者和授权快照。

### 例子 2：登录与授权限制

- 现状：未登录或禁止衍生的用户可能尝试复制公开模型。
- 提议后的行为：未登录用户先被引导登录；禁止衍生的授权阻止 Fork 并说明原因。
- 验收：未登录点击 Fork 时不创建副本；授权禁止衍生时按钮不可用并显示原因；登录且授权允许时才可确认。

### 例子 3：源模型状态与文件可用性

- 现状：源模型下架、未公开或文件损坏时仍可能产生不可用副本。
- 提议后的行为：只有当前仍公开、未下架且文件可用的源版本才能 Fork。
- 验收：对私有、审核中、审核未通过、已下架或文件不可用模型执行 Fork，均不创建副本并返回对应反馈。

### 例子 4：版本隔离与后续发布

- 现状：手动复制容易写回原模型或让 Fork 误自动公开。
- 提议后的行为：Fork 修改生成自己的新版本，Fork 在通过发布审核前保持私有；后续公开需要重新提交审核。
- 验收：修改 Fork 后，原模型的文件、版本和统计不变；尝试直接公开 Fork 被导向发布审核；源模型产生新版本时，已有 Fork 不自动变化。

### 例子 5：重复请求和源模型下架

- 现状：重复点击或网络重试可能生成多个意外副本。
- 提议后的行为：一次确认请求具备幂等性；源模型后来下架不会删除已完成的合法私有 Fork，但禁止新的 Fork。
- 验收：对同一确认请求重复提交只得到一个副本；源模型下架后再次 Fork 被拒绝，已有私有 Fork 仍可在授权约束下继续管理。

### 例子 6：修改后重新公开仍遵守授权

- 现状：只有许可名称的快照无法让系统判断 Fork 重新公开时的署名、商用和同许可要求。
- 提议后的行为：Fork 的每个后续版本继承不可变 `licenseSnapshot`；提交公开时按机器可读约束校验署名、商用和 share-alike 要求。
- 验收：对要求署名且 share-alike 的源模型完成 Fork 和修改后，缺少原作者署名或尝试改为不兼容许可的发布申请被拒绝；补齐署名并沿用兼容许可后才能进入审核。禁止衍生的模型始终不能创建 Fork。
