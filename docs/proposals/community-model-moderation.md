# 提案：管理员审核模型发布、驳回与下架

## 动机 / 用户故事

管理员需要处理用户提交的模型，决定通过或驳回；对于已经公开的模型，必要时可以下架。审核流程接收处于“审核中”的模型，输出“已公开”或“审核未通过”。公共模型库页面不属于本提案范围。

## 目标用户

- 审核员：查看待审核模型，执行通过、驳回或下架
- 模型作者：查看审核结果和原因，不能审核自己的模型
- 普通用户：不能进入审核页面

## 现有做法及不足

现有流程没有统一的待审核列表、审核版本锁定、驳回原因和下架追溯规则，容易出现审核对象被新版本替换、无原因驳回、重复操作或审核结果不一致的问题。

## 本期范围

本期做：

- 用户提交一个明确的模型 revision 后创建独立 `ReviewRequest` 并进入“审核中”，该状态不覆盖模型整体状态。
- 待审核列表展示封面、标题、作者、分类、提交时间和当前状态。
- 审核详情展示封面、3D 预览、标题、描述、作者、分类、标签、授权方式、Fork 权限、STL / 3MF 文件状态、提交时间和当前审核状态。
- 审核内容锁定到用户提交时的模型版本，后续新版本不能替换正在审核的版本。
- 审核员通过后原子更新模型当前公开 revision；审核新版本期间，旧公开 revision 继续可见。
- 审核员驳回模型时必须填写原因；作者可在“我的模型”中看到原因并修改后重新提交。
- 审核员可以对已公开模型执行下架；下架时必须填写原因并保留审核和下架历史。
- 通过、驳回和下架操作必须具备权限控制，并正确处理并发、重复点击和网络重试。

本期明确不做：

- 不做公共模型库页面、关键词搜索和分类筛选。
- 不做自动版权识别或 AI 内容审核。
- 不做举报处理、申诉和恢复上架。
- 不做批量审核和审核员角色管理后台。
- 不做评论、收藏、下载和 Fork 页面。

## 关键决策与依据

### 备选方案

1. 提交后直接公开。
   - 优点：发布路径短。
   - 缺点：无法在公开前控制内容质量和授权信息。
2. 只保留通过或驳回，不支持公开后的下架。
   - 优点：状态模型简单。
   - 缺点：无法处理已公开模型后续发现的问题。
3. 使用审核版本锁定、通过 / 驳回 / 下架状态和可追溯操作历史。
   - 优点：覆盖发布前和公开后的基本治理闭环，并能解释结果。
   - 缺点：需要处理状态转换、权限和并发幂等。

### 本期选择

选择方案 3。

原因：公开模型需要先经过人工审核，已公开内容也需要有下架能力；版本锁定、必填原因和操作历史可以避免审核对象漂移及结果不可追溯。

## 基本概念与信息结构

### 审核申请

- `model`: 被审核的模型
- `modelRevision`: 用户提交时锁定的模型版本
- `status`: 审核中、已通过或审核未通过
- `submittedAt`: 提交时间
- `reviewer`: 审核员
- `reviewedAt`: 审核时间
- `publishedAt`: 发布时间
- `reason`: 驳回或下架原因

`ReviewRequest` 独立于 `Model` 和 `ModelRevision`。通过申请时，系统在一次原子操作中把 `Model.publishedRevision` 切换为该申请锁定的 revision；驳回申请不改变当前公开 revision。下架是模型公开状态上的独立管理动作。

### 操作历史

记录每次有效的通过、驳回和下架操作，以及操作人、时间、目标版本和原因。重复请求不能生成重复的有效记录。

## 原型 / 演示

审核列表只显示等待审核的模型。详情页分为模型预览与发布资料、当前状态、操作区和历史记录。驳回或下架按钮打开必填原因输入；非审核员、模型作者审核自己模型或状态不正确时，操作不可用并显示原因。

## 验收标准

### 例子 1：待审核列表与版本锁定

- 现状：用户提交的模型没有稳定的审核入口，后续版本可能替换审核对象。
- 提议后的行为：模型提交后进入审核中，并以提交时的 `modelRevision` 固定审核内容。
- 验收：提交一个包含封面、标题、分类和文件的模型后，审核员能在待审核列表看到它；作者随后创建新版本，审核详情仍展示提交时的版本。

### 例子 2：权限限制

- 现状：未授权用户可能通过页面地址进入审核功能。
- 提议后的行为：只有审核员能查看审核列表、详情和执行审核操作；作者不能审核自己的模型。
- 验收：普通用户、未登录用户和模型作者访问审核列表或详情均被拒绝；审核员访问成功；审核员尝试审核自己提交的模型时被阻止。

### 例子 3：审核通过

- 现状：没有可追踪的公开发布结果。
- 提议后的行为：审核员通过后，模型进入已公开，并记录审核员、审核时间和发布时间。
- 验收：对审核中的模型点击通过，模型状态变为已公开，作者的模型列表显示已公开，且历史中只有一条有效的通过记录。

### 例子 4：驳回原因与重新提交

- 现状：没有原因的驳回无法帮助作者修改模型。
- 提议后的行为：驳回必须填写原因；驳回模型不进入公共展示，作者可以看到原因并修改后重新提交。
- 验收：不填写原因时驳回被阻止；填写“文件与描述不一致”等原因后驳回成功，普通用户不可见，作者能看到原因并重新提交。

### 例子 5：公开模型下架

- 现状：已公开模型出现问题后没有移除公共访问的闭环。
- 提议后的行为：审核员填写下架原因后，模型变为已下架，立即失去普通用户的查看、下载、收藏和 Fork 资格。
- 验收：下架后公共访问、下载、收藏和 Fork 均被拒绝；作者仍能在“我的模型”看到模型和下架原因；历史保留下架记录。

### 例子 6：并发、重复和非法状态

- 现状：并发点击或网络重试可能导致通过和驳回同时成功，或重复记录发布时间。
- 提议后的行为：同一个审核申请只有第一个符合当前状态的有效操作成功；后续请求返回“该申请已处理”类反馈。
- 验收：并发提交通过与驳回时只能有一个最终状态；重复点击通过不重复记录发布时间；对已下架模型再次下架或对已公开模型重复驳回均被拒绝。

### 例子 7：公开模型提交新版本

- 现状：若审核状态直接覆盖模型整体状态，新版本等待审核可能让旧公开版本意外消失。
- 提议后的行为：作者为已公开模型的新 revision 创建独立审核申请，旧 `publishedRevision` 在审核期间继续提供浏览和下载。
- 验收：模型 V1 已公开时提交 V2，审核列表锁定 V2，但公共详情继续返回 V1；驳回 V2 后仍公开 V1，通过 V2 后在一次原子更新中切换为 V2，任何时刻都不暴露未审核版本。
