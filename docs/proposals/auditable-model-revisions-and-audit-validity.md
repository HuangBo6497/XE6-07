# 提案：可打印性检查结果追溯、模型变更与下游使用限制

## 动机 / 用户故事

用户和后续流程需要始终使用与当前模型相匹配的检查结论。模型几何内容发生变化后，系统不能误用旧检查结果继续发布或切片。

## 目标用户

- 上传、修复或生成模型并需要查看检查结论的用户
- 使用检查结论作为发布检查或切片门禁的后续流程
- 需要追溯模型版本、变更原因和检查历史的运营或工程人员

## 现有做法及不足

如果检查结果没有绑定到明确的模型版本，模型修复后旧结论仍可能被误认为适用于当前模型；用户也无法区分当前版本和历史版本，难以解释某次检查结论的来源。

## 本期范围

本期做：

- 首次生成或上传的模型、每次修复后的模型都作为可追溯的模型版本保存，暂称 `AssetRevision`。
- 每份检查结果明确对应产生时的模型版本。
- 用户可以查看模型版本来源、变更原因、检查时间和检查结论。
- 模型几何内容发生变化时，旧检查结果标记为过期或不可继续使用。
- 当前通过可打印性检查的结果可以提供给发布检查和切片门禁使用。
- 旧检查结果保留为历史记录，但不能证明当前模型已经通过检查。

本期明确不做：

- 不做复杂版本树、多人合并或模型差异编辑器。
- 不删除历史模型和历史检查结果。
- 不实现发布审核或切片本身，只提供可追溯的检查结果和下游使用限制。
- 不要求本期确定具体字段、数据库或 API。

## 关键决策与依据

### 备选方案

1. 只保存模型当前状态和最近一次检查结论。
   - 优点：实现简单。
   - 缺点：无法追溯历史，也无法在几何变化后可靠失效旧结论。
2. 将模型变化保存为 `AssetRevision`，并把检查结果绑定到版本。
   - 优点：可追溯，能够明确失效边界，并为下游流程提供当前版本结论。
   - 缺点：需要保存版本和结果历史。

### 本期选择

选择方案 2。

原因：业务关键约束是“检查结论不能脱离产生它的模型版本”；版本绑定比覆盖式保存更能防止错误放行，同时保留历史查看能力。具体数据模型和 API 待讨论。

## 基本概念与信息结构

### `AssetRevision`

模型一次可追溯的内容版本，至少能说明来源、变更原因和产生时间。

### 检查结果

- `revision`: 对应的 `AssetRevision`
- `auditedAt`: 检查时间
- `conclusion`: 通过或其他检查结论
- `validity`: 当前有效、过期或不可继续使用

### 下游门禁

发布检查和切片只能消费当前模型版本对应的有效通过结果；历史或过期结果只能用于查看。

## 原型 / 演示

模型详情展示当前版本和历史版本列表。每份检查结果显示对应版本、来源、变更原因、检查时间、结论和有效性。下游发布或切片流程读取当前版本的有效结果，发现版本不匹配时阻止继续。

## 验收标准

### 例子 1：首次模型与检查绑定

- 现状：检查结果无法明确对应哪一份模型内容。
- 提议后的行为：首次生成或上传的模型保存为一个 `AssetRevision`，检查结果绑定到该版本。
- 验收：对模型 A 执行可打印性检查后，结果页面能同时显示模型 A 的版本来源、检查时间和结论；历史记录能通过该版本找到结果。

### 例子 2：修复产生新版本

- 现状：模型修复后仍可能沿用旧检查通过结论。
- 提议后的行为：改变几何内容的修复生成新的 `AssetRevision`，旧结果变为过期或不可继续使用。
- 验收：模型 A 检查通过后改变几何内容，系统显示新版本；旧检查明确标记过期，不能作为当前模型的通过证明。

### 例子 3：当前有效结果供下游使用

- 现状：发布检查和切片无法判断结果是否属于当前模型。
- 提议后的行为：下游只接受当前版本对应的有效通过结果。
- 验收：新版本重新检查通过后，发布检查和切片门禁可以读取该结论；使用旧版本结果时流程被阻止并返回版本不匹配反馈。

### 例子 4：历史追溯

- 现状：用户无法查看模型如何变化或某次检查何时产生。
- 提议后的行为：历史模型版本和检查结果保留，可查看来源、变更原因、时间和结论。
- 验收：用户从当前模型进入历史记录，能看到模型 A 的原始版本、修复版本及其各自检查结果，且历史结果不会被新版本覆盖。

### 例子 5：非法情况

- 现状：删除或伪造版本关联可能让无效结果被当作当前通过依据。
- 提议后的行为：没有对应版本、版本已变化或结果已过期时，不得放行发布或切片。
- 验收：提交缺少 `revision` 的检查结果、引用不存在版本或使用过期结果时，系统拒绝将其作为门禁通过依据，并给出明确原因。
